# SHOWDOWN: план закрытия публичного доступа к данным Supabase

Дата: 2026-09-04. Текущий локальный подэтап: 2.3h — защищённая регистрация на турнир.

Статус: локальная среда и первый этап персональной авторизации реализованы.
Окончательное закрытие legacy-доступа и часть серверных финансовых операций ещё не готовы.
На production изменения не применялись; публиковать этот промежуточный этап нельзя.

## Контрольная точка 2.3b — открытые политики заменены локально

- Удалены все шесть legacy-политик `FOR ALL USING (true) WITH CHECK (true)`.
- Добавлены отдельные политики чтения/записи для профилей, турниров, участников,
  финансов, журнала и таймера. Они используют подтверждённую сервером учётную
  запись и роль из `club_private.profile_roles`, а не флаги браузера/JWT metadata.
- Пользователь видит собственные финансовые строки и может создать/удалить только
  собственную безопасную запись на открытый турнир. Управление турнирами и таймером
  предназначено администраторам; полный журнал читается только SuperAdmin.
- У клиентских ролей отозваны TRUNCATE/REFERENCES/TRIGGER и ненужные операции:
  транзакции доступны напрямую только для чтения, журнал — чтение/добавление,
  таймер — чтение/добавление/изменение. Окончательный запрет прямой записи журнала,
  баланса и защищённых полей выполняется в четвёртом пункте после переноса legacy-путей.
- Миграция откатывается при неизвестной публичной политике и после применения
  проверяет отсутствие безусловных TRUE-выражений. Повторное применение идемпотентно.
- Полный регресс после установки политик: 97/97 интеграционных тестов прошли.
  Дополнительный набор anon/RLS: 24/24, включая прямую матрицу User/Admin/SuperAdmin.
  TypeScript тестов, lint и `diff --check` прошли. Production не изменялся.

## Контрольная точка 2.3c — User / Admin / SuperAdmin

- Серверным источником роли остаётся закрытая `club_private.profile_roles`, связанная
  с подтверждённым `auth.uid()`. `is_admin`, email/localStorage и JWT user metadata
  не являются источником полномочий.
- Новая и непривязанная учётная запись получает только `user`. Существующие флаги
  администраторов сохраняются при первичном переносе и повторной миграции.
- User и Admin не могут менять роли. Только SuperAdmin вызывает ограниченную команду
  назначения/снятия Admin; клиент не может назначить SuperAdmin, а существующий
  SuperAdmin защищён от понижения через эту команду. Действие журналируется сервером.
- Административные серверные команды повторно проверяют актуальную роль, поэтому
  ранее выданный токен перестаёт давать доступ после отзыва Admin. Полный журнал
  дополнительно ограничен политикой SuperAdmin и проверкой маршрута интерфейса.
- Эти гарантии покрыты foundation-тестами и прямой RLS-матрицей; полный набор
  97/97 и целевой набор 24/24 прошли. Реальную учётную запись SuperAdmin миграции
  не выбирают и не меняют — это отдельное production-решение с подтверждением.

## Контрольная точка 2.3h — регистрация игрока

- Запись и отмена записи выполняются `club_set_registration` по подтверждённому
  пользователю. Клиент не передаёт user ID, никнейм, рейтинг или идентификатор
  строки участника; сервер берёт их из сессии и профиля.
- Блокировка турнира сериализует конкурентную борьбу за последнее место. Закрытый
  турнир и отмена записи уже получившего место игрока отклоняются. Устойчивый UUID
  защищает от двойного действия после неопределённого сетевого ответа.
- Обычная роль больше не имеет прямых INSERT/DELETE-политик `participants`.
  Запрещённый RLS DELETE может вернуть успешный пустой HTTP-ответ PostgREST, поэтому
  тест дополнительно подтверждает, что строка не видна и остаётся в базе.
- 6/6 целевых и 117/117 полных интеграционных тестов, 110/110 модульных тестов,
  TypeScript и lint прошли. Прямое административное управление
  составом пока сохраняется до переноса соответствующих команд. Production не изменялся.

  требуют отдельного одобрения.
- Не удалять пользователей, администраторов, транзакции, турниры и журнал.
- Не менять существующие идентификаторы профилей или связи между таблицами.
- Не читать и не переносить production-секреты в локальное окружение. Не

- Тесты используют только искусственные данные и локальные адреса. Рабочее
  приложение не запускать против production API для проверки миграции:
  существующий запуск содержит массовое обновление пользователей.
- При неожиданном состоянии схемы, неоднозначной привязке профиля или риске
  потери прав остановиться и запросить решение; не исправлять данные наугад.

## Целевая модель

### Персональная сессия и привязка профиля

1. Сохранить привычную доставку кода через серверный OTP endpoint.
2. После успешной одноразовой проверки кода получать стандартную сессию
   Supabase Auth на сервере. Предпочтительный технический вариант:
   административный `generateLink` и серверный `verifyOtp` для уже подтверждённой
   почты; совместимость проверить на изолированном Supabase до внедрения.
3. Не создавать собственную схему подписи JWT и не выдавать `service_role`
   клиенту. Административные токены, ссылки и хеши в ответ клиенту не включать.
4. Связывать Auth UUID с существующим `users.id` через отдельную уникальную
   связь, устанавливаемую сервером. Исходный `users.id`, история и `is_admin`
   сохраняются. Email для первой привязки брать из подтверждённой сервером
   учётной записи, а не из параметра клиента.
5. Проверять подтверждение email, уникальность нормализованной почты и отсутствие
   чужой привязки. При коллизии ничего не сливать и не переносить автоматически.
   После привязки работать по неизменяемому Auth ID, а не повторно по email.
6. Создавать новые профили только серверной операцией с обычной ролью.
   Убрать клиентское повышение прав и правило «первый пользователь — админ».
7. Клиент использует access/refresh token Auth, обрабатывает восстановление,
   обновление и завершение сессии с ограниченным временем ожидания.
   Старый localStorage не открывает доступ: потребуется повторный вход по коду.
8. Не открывать `users` ради проверки существования email до входа. Проверку
   необходимости регистрации/согласий выполнять после подтверждения почты;
   существующие согласия сохранять. Содержание документов не менять.

### Матрица прав — проект для реализации

| Возможность | Без входа | Пользователь | Администратор | SuperAdmin |
| --- | --- | --- | --- | --- |
| Запрос и проверка кода | С лимитами | С лимитами | С лимитами | С лимитами |
| Собственный полный профиль | Нет | Да | Да | Да |
| Список игроков/рейтинг | Нет | Без приватных полей | В рамках админских задач | Да |
| Изменение собственного обычного профиля | Нет | Разрешённые поля | Разрешённые поля | Разрешённые поля |
| Турниры и участники | Нет | Просмотр, запись/отмена только себя | Управление | Управление |
| Финансы и начисления | Нет | Только разрешённые собственные данные/операции | Серверные операции | Серверные операции |
| Выдача/отзыв роли администратора | Нет | Нет | Нет | Серверная операция |
| Чтение полного журнала | Нет | Нет | Нет | Да |
| Прямое изменение ролей, баланса, финансов и журнала | Нет | Нет | Нет | Нет |

Роли приложения не должны становиться PostgreSQL `superuser` или клиентским
`service_role`. Даже SuperAdmin действует через ограниченные серверные операции.
Чтение полного журнала сейчас предназначено для SuperAdmin; это сохраняется.
Конкретную учётную запись SuperAdmin подтвердить отдельно; не выбирать её
по времени регистрации, значению в браузере или догадке. Существующее особое
клиентское правило учесть при переносе, чтобы не лишить владельца доступа.

### Права БД и RLS

- Одной согласованной миграцией отозвать широкие права на бизнес-таблицы у
  `PUBLIC`, `anon`, `authenticated` и выдать минимальный необходимый набор.
  Учесть права на отдельные колонки, последовательности, функции и будущие объекты.
- Удалить именно проверенные открытые политики и создать отдельные политики
  для разрешённых операций. Не считать новое ограничение действенным, пока
  остаётся старая разрешающая политика.
- RLS привязывает доступ к проверенному `auth.uid()` и серверной роли. Отсутствие
  или истечение сессии, непривязанный профиль и неизвестная роль закрывают доступ.
- Разрешить прямое обновление только явно перечисленных безопасных колонок
  собственного профиля. Роль, email/привязка Auth, баланс, инвентарь, начисления
  и уведомления не входят в этот список.
- Для каталога игроков, турниров и участников выдавать безопасную проекцию:
  не раскрывать чужую почту, дату рождения, уведомления и служебные комментарии.
  Скрытие полей только в React недостаточно; защищается ответ API.
- Для функций с повышенными правами: фиксированный `search_path`, проверка
  субъекта и полномочий внутри функции, разрешённые параметры, минимальный
  `EXECUTE`, отсутствие универсального SQL/табличного прокси.
- OTP-функции оставить серверными. Обновить исходные SQL-сценарии, чтобы повторный
  запуск старого bootstrap не восстановил открытые разрешения.

### Защищённые операции и совместимость

- Роли: отдельная серверная команда; журналирование исполнителя; защита от
  самоповышения и потери последнего SuperAdmin. Миграция не понижает текущих админов.
- Финансы: разрешённые серверные команды создания/корректировки с валидацией,
  атомарностью и журналом. Не принимать произвольный объект для обновления БД.
- Баланс: серверное начисление/списание; защита от повторной выплаты и потери
  обновлений при одновременных запросах. Покупка — по ID товара и серверной цене,
  не по переданному клиентом новому балансу.
- Награды: получение существующего уведомления ровно один раз; начисление по
  подтверждённому сервером основанию. Сохранить суммы и правила расчёта наград.
- Журнал: запись сервером в транзакции вместе с действием; исполнителя и время
  определяет сервер. Клиент не может подделывать автора, вставлять, менять или
  удалять записи. Не добавлять очистку журнала. Существующее удаление пользователей с
  финансовой историей не переносить как массовое удаление без отдельного решения.
- Турнирные выплаты: перенести проверку повторного распределения и расчёт на
  сервер, согласовав обновление результата, баланса и журнала в одной транзакции.
- Массовый сброс косметики/баланса убрать из пути запуска клиента. Имеющийся
  отдельный SQL сброса не запускать, данные не «нормализовать» автоматически.
- Таймер: создать отдельное защищённое хранилище и отказаться от записи состояния
  через `logs`. Существующий снимок сохранять только после проверки формата,
  не удаляя исходную запись журнала. Учесть синхронизацию и Realtime.
- Административные маршруты оградить на клиенте для UX, но все полномочия всё
  равно проверять на сервере. Ошибка API не должна показываться как успешная запись.

## Последовательность реализации и контрольные точки

### 2.0 — изолированное окружение

- Поднять локальный PostgreSQL/Supabase на loopback, в отдельном проекте и томах.
  Не использовать production credentials, подключения или копии реальных профилей.
- Создать искусственные роли и данные: обычные пользователи, несколько
  администраторов, SuperAdmin, финансы, награды, таймер.
- Для unit-тестов запретить реальные сетевые запросы и загрузку production `.env`.
- Проверить исходную сборку/тесты и доступность тестовой БД до написания миграций.

### 2.1 — сессии и роли

- Реализовать серверную выдачу сессии, безопасную привязку профиля, регистрацию,
  завершение сессии и серверное определение роли.
- Добавить тесты неверного/повторного OTP, истёкшей сессии, подмены localStorage,
  коллизии email, повторного/одновременного входа и сохранения администраторов.

### 2.2 — серверные операции

- Перевести защищённые записи и зависимые сценарии на серверные команды.
- Проверить магазин, награды, выплаты, журнал, админские действия и таймер.
- Никаких вызовов этих команд на production в ходе разработки.

### 2.3 — закрытие доступа и негативные тесты

- Применить миграции исключительно к тестовой БД.
- Проверять права реальными ролями `anon`/`authenticated`, а не только владельцем
  БД: чтение чужих полей, изменение ролей/баланса, запись и удаление журнала,
  запрещённые RPC, подмену userId, обход через представления/Realtime.
- Проверить атомарность, конкурентные покупки и повторные финансовые запросы.
- Сравнить IDs, количество и права исходных тестовых администраторов до/после.
- Повторить интеграционные проверки входа через Auth/API на изолированном Supabase.
- Проверить браузерные сценарии и мобильные размеры; эмуляцию не выдавать за
  тест на физическом Android/iPhone. Реальные устройства проверить отдельно.

### 3 — подготовка production, отдельное одобрение

- Установить ревизию опубликованного клиента и способ его публикации. Сверить
  актуальную схему и эффективных администраторов без вывода персональных данных.
- Отдельно подтвердить SuperAdmin и спорные полномочия/деструктивные операции.
- Создать защищённые резервные копии БД и нужной конфигурации, проверить восстановление
  в изоляции. Не скачивать реальные данные локально без отдельного разрешения.
- Согласовать окно переключения, краткое ограничение записей и повторный вход.
- Подготовить версии клиента/функций, миграцию, контрольные запросы и план отката.
  Не выполнять до отдельного подтверждения пользователя.

### 4 — переключение и проверка, отдельное одобрение

- Согласованно переключить клиент, серверные команды и разрешения БД. Избежать
  состояния, когда старый клиент остался без доступа, а новый ещё не опубликован.
- Проверить вход действующих администраторов и пользователя, затем отсутствие
  анонимного доступа и работоспособность критических сценариев.
- Защиту панели выполнить отдельным согласованным действием: обеспечить доступ
  через защищённый канал, отделить панель от необходимых публичных API-маршрутов,
  сохранить рабочий HTTPS API и SSH. Конкретные правила — после проверки маршрутов.

## Откат

- До переключения зафиксировать версии, точные ACL/политики и проверенные резервные
  копии без размещения содержимого секретов или данных в Git.
- При сбое остановить переключение и при необходимости записи; сохранять данные,
  новые Auth-связи и журнал. Не удалять новые таблицы/учётные записи ради отката.
- Предпочитать исправление или возврат совместимой версии приложения при сохранении
  закрытого доступа. Не восстанавливать автоматически `grant all`/открытые политики.
- Восстановление всей БД из копии может потерять записи после копирования: только
  по отдельному решению с учётом новых данных, не как штатный первый шаг.

  сервер, не доверяет старым email/userId как доказательству входа. Убраны повышение

- 2.2a: добавлена миграция `20260903_finance_commands.sql` и клиентские вызовы
  серверных команд создания счёта/билета и отметки оплаты. Сумма (1000 рублей;

  доступности аддона перенесено из существующего UI без изменения тарифа.
  Журнал пишется в той же транзакции; отдельные клиентские записи для этих действий убраны.
- Повтор одного запроса создания с тем же идентификатором не создаёт новый счёт.
  Одновременные оплаты не дублируют журнал и не изменяют дату уже принятой оплаты.
  Клиент сохраняет идентификатор неясно завершившегося запроса в `sessionStorage`
  до отправки и восстанавливает его после перезагрузки той же вкладки. Ключ — SHA-256

  только после подтверждения. Закрытие вкладки, очистка хранилища и другое устройство
  пока не покрыты: перед новым счётом нужна сверка кассы. Это не механизм авторизации.
- 2.2b: миграция `20260903_registered_dealer_hours.sql` хранит часы зарегистрированного
  игрока отдельно от счетов. Первоначально переносится прежний максимум часов по
  паре турнир/игрок, без изменения исходных финансовых строк. Повтор миграции не
  перезаписывает уже сохранённые часы; время изменения не подменяется датой оплаты.
  Команда администратора ±0,5 часа проверяет права, сериализует конкурентные запросы,
  защищена от повторов и атомарно записывает журнал. Счета наследуют часы даже при
  одновременном создании; изменение часов не меняет сумму, статус и дату оплаты.
- Клиент показывает часы после подтверждения сервера, хранит UUID незавершённой
  операции при перезагрузке той же вкладки и не принимает более старую ревизию часов.
  Новый `club_finance_snapshot` выдаёт обычному пользователю только его финансы/часы,
  администратору — общий набор. Клиент больше не читает кассу прямым SELECT таблицы;
  видимая вкладка обновляет снимок каждые 15 секунд. Ошибка кассы отображается явно.
- 2.2c: миграция `20260903_transaction_voids.sql` заменяет удаление счёта/билета
  серверной отменой с обязательной причиной. Исходная строка, сумма, статус и дата
  оплаты сохраняются; отдельная закрытая запись содержит снимок исходной строки,
  автора, причину и время отмены. Журнал записывается атомарно с отменой.
  Повторная отмена не меняет первоначальную причину/автора/дату. Отмена оплаченной
  записи корректирует активный реестр, но НЕ выполняет и НЕ регистрирует возврат денег.
- Оплата и отмена блокируют одну и ту же строку: уже отменённую запись нельзя оплатить.

  Повтор создания возвращает текущее состояние, включая отмену. Обычному игроку
  сервер выдаёт отметку отмены только своих записей, без административной причины.
- Клиент больше не удаляет финансовые строки напрямую: ждёт подтверждения отмены,
  исключает её из действующих счетов, долгов, выручки, билетов и статистики.

  Поздние ответы не возвращают отменённый счёт в активные. При экспорте текстовые

- `club_equip_item` проверяет владение платным предметом, разрешает базовые бесплатные
  предметы и не принимает адрес изображения или значения второго слота от клиента.
  Общая запись профиля больше не принимает поля инвентаря/внешнего вида; магазин
  больше не пишет свой журнал из браузера. Клиентские картинки остаются прежними,
  но отображаемые цены и доступность приходят из серверного каталога.
- `club_claim_ruby_notification` принимает только ID существующего бонуса своего
  пользователя. Сумма/сообщение берутся из сохранённого уведомления. Сервер хранит
  исходную запись в закрытой таблице получения бонусов и не зачисляет её повторно.
  Убирается только полученное уведомление; остальные сохраняются. Неизвестные,
  неоднозначные ID, отрицательные/дробные суммы и переполнение баланса отклоняются
  без исправления или удаления исходных данных. Бонус и покупка используют одну
  блокировку профиля, поэтому их одновременное выполнение не теряет кредит/списание.
- `club_wallet_snapshot` возвращает только собственный кошелёк, в том числе для
  администратора. Клиент проверяет владельца и подтверждение операции; баланс и
  каталог имеют независимые ревизии для защиты от поздних ответов. Ревизия кошелька
  отслеживает также оставшиеся legacy-изменения баланса — это совместимость, а не
  разрешение считать эти старые пути защищёнными. UUID запроса магазина сохраняется
  в той же вкладке по хешу намерения/подтверждённого профиля, без записи секретов.
- В магазине и окне бонуса кнопки заблокированы до подтверждения; ошибки загрузки
  видны явно. Надпись бонуса исправлена на «К получению»: деньги ещё не прибавлены
  к балансу до подтверждённой операции. При смене пользователя прежний кошелёк
  не используется. Физические устройства и полный браузерный UI пока не проверялись.
- Важная граница 2.2e: `rubyGrants.ts`, административное `addCoins` и начисления
  при закрытии турнира пока сохраняют legacy-пути изменения баланса/уведомлений.
  Их нельзя использовать совместно с новым магазином в production до полного
  переключения. Следующий подэтап — серверные административные начисления и выплаты;
  остаточные широкие ACL/RLS по-прежнему не отозваны.
- Общий прогон 2.2e: 103 модульных и 74 интеграционных теста (11 новых модульных и
  13 новых интеграционных для кошелька), TypeScript приложения/Edge Functions/новых
  тестов, lint изменённых файлов и изолированная сборка прошли. Сохраняется предупреждение
  сборки о размере chunk; браузерные/физические мобильные сценарии ещё не проверены.
- Остаются 2.2 и 2.3: административные начисления/награды/турнирные выплаты,
  управление турнирами/участниками, разрешённые изменения профиля, оставшийся журнал,
  защищённое хранилище таймера и окончательный отзыв широких прав с RLS-тестами.
  Дилеры без привязки к профилю не объединялись с пользователями автоматически.
  Миграция-основа намеренно не заявляется завершённым закрытием доступа: legacy
  `grant all` и открытые политики ещё существуют. Применять её отдельно в production нельзя.
- Production, панель, реальные профили и администраторы не изменялись. Локальная
  работа продолжается без новых запросов разрешения; перед production остаётся
  отдельная контрольная точка с одобрением пользователя.
